# Intégration continue et candidat de déploiement

`.github/workflows/ci.yml` vérifie les trois applications sur Node 22.23.4 avec cache npm par lockfile. Le job MySQL initialise un service 8.4 isolé, copie sa clé publique, génère la clé de confirmation de recette et exécute la suite intégrée. L’API et le Web échouent sur une alerte npm de gravité haute ou critique. Expo exécute Doctor et la vérification de compatibilité SDK. Suivre séparément les [alertes Expo restantes](SECURITY_AUDIT.md).

`.github/workflows/release-candidate.yml` se lance manuellement avec une URL HTTPS d’API. Il réexécute la CI et publie deux archives contrôlables par SHA-256 pour le commit indiqué. Le Web est construit avec l’URL donnée. Télécharger l’artefact, vérifier `sha256sum -c SHA256SUMS` et examiner la liste des fichiers avec `tar -tzf` avant extraction. L’archive API contient les scripts nécessaires au seed et au bootstrap. Garder les archives approuvées dans le dépôt d’artefacts de l’équipe avant échéance.

Protéger la branche principale avec les jobs de vérification obligatoires et les revues, et préparer des environnements GitHub `preproduction` et `production` à secrets et droits distincts. Avant d’ajouter une étape d’envoi sur Plesk, définir le compte dédié, limiter ses droits au vhost et aux releases autorisées, vérifier l’hôte SSH et protéger la production par un réviseur requis et une approbation explicite. Promouvoir le même candidat API après préproduction. Comme l’URL Web est intégrée à la compilation, reconstruire le candidat Web de production pour le même commit et vérifier son empreinte. Conserver les versions précédentes et journaliser le commit et les migrations appliquées. [Environnements GitHub Actions](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).

Le workflow de préparation ne se connecte à aucun serveur. L’application des migrations et l’activation sur la cible suivent la [procédure Plesk](DEPLOYMENT_PLESK.md).
